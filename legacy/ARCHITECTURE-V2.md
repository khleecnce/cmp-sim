# FabSim 아키텍처 V2 — 5파트 구조 + 병합 파라미터

> **정본.** 2026-09-08 사용자 지시로 전면 재설계. V1(`agents/ORG.md` 28개 에이전트 ·
> 노트 78편)의 문제는 노트 품질이 아니라 **엔진 연결률 9% (41/468 필드)** 였다.
> `--sensitivity`에서 살아있는 인자가 다운포스·플래튼RPM·r_cc 3개뿐 —
> Preston 식(MRR=Kp·P·V) 그 자체다. pH·입자크기·패드조도 전부 탄성도 0.
> **슬러리 소재 개발자용 도구인데 슬러리 인자가 하나도 안 먹혔다.**
>
> V2는 조직을 학습량이 아니라 **엔진 반응성**을 축으로 다시 세운다.

## 0. 최상위 — 무엇을 만드는가

**시뮬레이션 프로그램이 메인 잡이다.** 학습·조직·게이트는 전부 그것을 위한 수단이며,
관리 도구를 만드느라 산출물을 미루는 패턴은 금지한다(V1의 실패 원인).

화면은 **실제 장비 모양**이다. 플래튼이 돌고, 캐리어가 웨이퍼를 물고 회전하고,
슬러리가 암에서 흘러 그루브를 타고 번지고, 컨디셔너 디스크가 스윕한다.
**각 부분을 클릭하면 그 파트의 설정 패널이 열린다.**

```
        ┌──────────────────────────────────────────────┐
        │   3D 뷰 (three.js) — 클릭 가능한 5개 핫스팟   │
        │                                              │
        │    [캐리어/헤드]──웨이퍼      슬러리 암 ──┐   │
        │         ↓ 하중                          ↓   │
        │    ╔═══════════════════════════════════════╗ │
        │    ║        플래튼 + 패드 (그루브)          ║ │
        │    ╚═══════════════════════════════════════╝ │
        │              ↑ 컨디셔너 디스크 (스윕)         │
        └──────────────────────────────────────────────┘
             │        │        │       │        │
          ①장비    ②슬러리   ③패드   ④디스크  ⑤웨이퍼
```

## 1. 5개 파트 (입력 도메인)

각 파트는 **입력(사용자가 정함)** 과 **출력(저절로 도출됨)** 을 구분한다.
출력을 입력칸에 두면 거짓 UI다(V1 demo_app의 film 드롭다운이 그랬다 — 골라도 Kp가 안 변했다).

### ① 장비 (Equipment) — `tool`
실제 폴리셔(AMAT Reflexion/Mirra, Ebara, 荏原)에서 오퍼레이터가 만지는 값.

| 입력 | 단위 | 비고 |
|---|---|---|
| 다운포스 / 존별 압력 | psi | 존 3~5개(AMAT Titan/Contour 헤드) |
| 리테이닝 링 압력 | psi | 엣지 프로파일 지배 |
| 이너튜브/멤브레인 압력 | psi | |
| 플래튼 RPM | rpm | |
| 캐리어(헤드) RPM | rpm | Rs = 헤드/플래튼 비 |
| 헤드 스윕 / 오실레이션 | mm, cpm | |
| SFR (슬러리 유량) | mL/min | |
| 슬러리 분사 위치 | mm (반경) | POU 지점 |
| 컨디셔너 다운포스 | lbf / N | **장비 설정** (디스크 형상은 ④) |
| 컨디셔너 스윕 범위·속도 | mm, cpm | |
| 컨디셔닝 모드 | in-situ / ex-situ / duty% | |
| 플래튼 온도 제어 | °C | 있는 툴만 |
| 연마 시간 / EPD 모드 | s | |

| 입력 | 범위 예 |
|---|---|

| 등전점 IEP | pH |
| **첨가제** oxidizer | H2O2 · KIO3 · Fe(NO3)3 · persulfate — wt% / mM |
| R/R booster (막질별) | 아미노산(glycine·alanine) · 유기산 — mM |

## 2. 병합 파라미터 (Merged Factors) — V2의 핵심

### 문제
입력 필드가 468개다. "무엇이 결과를 어떻게 바꾸는지" 파악이 불가능하다.

### 해법
**연관 인자를 물리적으로 묶어 소수의 파라미터로 만든다.**
각 파라미터는 ①결과를 어떻게 바꾸는가 ②그것을 바꾸려면 무엇을 만져야 하는가를 동시에 답한다.

### 분리 규칙 (사용자 확정)
- **장비는 소모품 3종(슬러리·패드·디스크)과 묶이지 않는다.** 축이 다르다 —
  장비는 *부하를 가하고*, 소모품은 *그 부하에 반응한다*. 섞으면 "슬러리를 바꿔야 하나
  RPM을 올려야 하나"에 답할 수 없다.
- **웨이퍼는 제외.** 디폴트 대상값.

### 2축 구조

```
   성능 = f( 장비축 E[4개]  ×  소모품축 C[6개] )        웨이퍼 = 고정 대상
```

#### 장비축 (Equipment Factors) — 소모품과 섞지 않음

| 기호 | 이름 | 정의 (물리) | 무엇을 만지나 |
|---|---|---|---|
| **Λ** | 기계 부하 강도 <br>Mechanical Load | `P × V` (Preston 곱). 단위면적 마찰일률 | 다운포스, 플래튼 RPM, 헤드 RPM, r_cc |
| **Π** | 반경 하중 분포 <br>Load Profile | 존압력·리테이너링에서 나온 `P(r)/P̄`의 형상 (기울기·엣지비) | 존별 압력, 리테이닝링 압력, 헤드 스윕 |
| **Θ** | 열·유동 부하 <br>Thermal-Flow | 마찰 파워 − SFR 냉각 → ΔT, 그리고 슬러리 공급 충분도 | SFR, 분사위치, 플래튼 온도제어, Λ |
| **Γ** | 컨디셔닝 부하 <br>Conditioning Duty | 디스크가 패드에 가하는 단위시간 절삭일 (force × sweep × duty) | 컨디셔너 하중, 스윕 범위·속도, in-situ/duty% |

#### 소모품축 (Consumable Factors) — 슬러리·패드·디스크가 함께 결정

| 기호 | 이름 | 정의 (물리) | 슬러리 | 패드 | 디스크 |
|---|---|---|---|---|---|
| **κ** | 접촉 강도 <br>Contact Intensity | 활성 입자 수 × 입자당 압입깊이. `δ_p = F/(2πR·H)`, `MRR ∝ H^-1.5` | 입경, 함량 | 경도, 탄성률, 기공 | 그릿밀도→asperity 밀도 |
| **χ** | 화학 반응성 <br>Chemical Drive | 표면 연화·산화 속도 (기준조성 대비 **배수**) | oxidizer, pH, booster, chelator | — | — |
| **ψ** | 표면 보호도 <br>Passivation | inhibitor 피복률 → 정지마찰/디싱 억제 | inhibitor, surfactant | — | — |
| **τ** | 슬러리 전달 <br>Transport | 접촉부에 도달하는 신선 슬러리 유효분율 | 점도, 고형분 | 그루브 depth/pitch, 기공 | 표면 텍스처 |
| **Δ** | 손상 유발도 <br>Damage Propensity | 스크래치·결함 발생 확률 | 대입자 tail D99, 응집 | 패드 debris | 그릿 탈락 |
| **S** | 시간 안정성 <br>Stability | 연속 연마 중 MRR 드리프트 | 응집·shelf | 마모·glazing | CR/WR 균형 |

### 이 설계가 답하는 질문
- **"κ를 올리려면?"** → 패드를 더 단단하게(Shore D↑) 하거나, 입자 함량↑, 또는 디스크
  그릿밀도↑로 asperity를 늘린다. 세 경로의 비용·부작용(Δ↑)이 다르다.
- **"MRR은 올리되 스크래치는?"** → κ↑ 대신 χ↑ (화학 경로). Δ가 안 따라 올라간다.
- **"장비로 될 일인가 소모품으로 될 일인가"** → Λ 탄성도와 κ 탄성도를 비교한다.
  축이 분리돼 있어야 이 비교가 성립한다. **이것이 장비를 섞지 않는 이유다.**

### 구현 규칙
1. `sim/factors.py`가 정본. 각 팩터는 `value` + `drivers`(어떤 필드에서 왔나) +
   `confidence` + `source`를 신고한다.
2. **모든 팩터는 기준 조성/기준 조건에서 정확히 1.0** (χ가 절대값이면 Kp에 이미 반영된
   효과를 두 번 센다 — V1에서 Cu MRR이 20배 붕괴한 원인).
3. 팩터를 붙였으면 **파라미터를 스캔해 응답 곡선을 눈으로 확인**한다. 단위테스트 통과는
   증거가 아니다(Langmuir θ가 1mM에서 0.97로 포화해 2mM과 5mM이 구분 안 됐던 전례).
4. 미연결 입력은 조용히 버리지 않고 **경고로 돌려준다**.

## 3. 5개 리서치 부문 (조직 재편)

V1은 28개 에이전트가 트리로 얽혀 "완주"를 생산했지만 엔진에 안 꽂혔다.
V2는 **5개 파트 = 5개 리서치 부문**으로 1:1 대응시킨다.

```
                  cmp-architect  (통합 · 병합 파라미터 소유 · 협업 조정)
                          │
   ┌──────────┬───────────┼───────────┬──────────┐
  R1장비     R2슬러리    R3패드     R4디스크    R5웨이퍼
 (Λ Π Θ Γ)  (χ ψ Δ_s)  (κ_p τ_p)  (Γ_d κ_d)  (기준선·판정)
```

**협업이 필수인 이유:** 병합 파라미터는 한 부문이 소유하지 못한다.
κ는 슬러리(입자) × 패드(경도) × 디스크(asperity)의 곱이다.
→ 팩터마다 **주담당 1 + 공동담당 n** 을 명시하고, 공동 산출물(`knowledge/factors/κ.md`)에
각자 자기 몫을 채운다. 예: **물리(접촉역학) + 화학(표면연화)을 접목해 슬러리에 적용.**

### 완주 판정 교체 — 학습량 → 엔진 반응
V1: "단원 6개 이수 = 완주". → 노트만 쌓이고 제품은 안 움직였다.
V2: 아래 **셋 다** 충족해야 완주.
1. 담당 축이 `--sensitivity`에서 **탄성도 ≠ 0** (미모델링 탈출)
2. held-out 데이터셋에서 **순위 재현 ρ ≥ 0.6**
3. 담당 파라미터 **confidence ≥ literature**

## 4. 기존 자산 처리
- 노트 78편(형식통과 66 · 주장검증 62)은 **버리지 않고 5개 섹션에 재분배**한다.
- 분배 완료된 노트는 프론트매터에 `v2_section: R2-slurry` + `v2_migrated: true`를
  달고, 원래 위치 문서 상단에 주석으로 이관 사실을 남겨 향후 혼동을 막는다.
- 팩(`knowledge/params/*.yaml`) 6종과 검증 테스트는 그대로 승계.

## 5. 미결 — 사용자 확인 필요
- "힉스필드"가 무엇을 뜻하는지 확인 필요. 3D 유체 표현을 위해 실제 물리 솔버(SPH 등)를
  붙일지, 셰이더 기반 시각 근사로 갈지의 선택으로 이해하고 **우선 셰이더 근사**로 간다
  (브라우저에서 60fps, 의존성 0). 실물리 유체가 필요하면 별도 배치 계산으로 분리한다.
